# ADR 007 · Uso de event sourcing

Fecha: 2020-10-30

## Estado

Propuesto

## Contexto

Food Farmacy trabaja con usuarios individuales externos y depende de su reputación. En ese entorno, el tiempo y la precisión para resolver reclamos de usuarios son esenciales. Por lo tanto, tiene que haber una forma de almacenar todos los cambios intermedios que se usan. Guardar solo el estado final de una entidad de dominio no ayuda a entender cómo terminamos en un estado específico.

El sistema de órdenes va a evolucionar a medida que la empresa crezca, y no todos los aspectos están claros al principio. Debe existir una opción de migración gradual de un modelo de datos y completitud de datos a otro.

El engagement del usuario es un objetivo de negocio y deben existir datos para analizar las acciones y comportamientos del usuario y construir un mejor modelo para nuevos engagements.

## Alternativas

**Uso de snapshots**

Un enfoque muy conocido que se usa desde hace años. Puede haber sistemas separados que registren las acciones de los usuarios y el estado más reciente de las entidades correspondientes. Usualmente las acciones de los usuarios ni siquiera se registran, y solo el estado final se presenta como fuente de verdad. En caso de errores de programación con ese enfoque, es posible llegar a un estado incorrecto de la entidad, o resulta imposible reconstruir cómo la entidad terminó en el estado presentado. Los logs de aplicación no ayudan mucho o son demasiado engorrosos para investigar un caso particular.

Por el otro lado, ese enfoque es fácil de implementar y normalmente no requiere conocimiento especial.

En el caso de registrar todos los eventos y manejar snapshots, se requiere gestión manual y correlación de esas acciones. Prevemos complejidad innecesaria en este caso y mayor probabilidad de cometer errores desde el punto de vista de programación. Las actualizaciones transaccionales correlacionadas van a tener un impacto significativo en la performance.

**Event sourcing**

Un enfoque bastante nuevo para muchos desarrolladores. De hecho, algunos beneficios y desventajas ya fueron descritos para el uso de snapshots. Sin el soporte de una herramienta dedicada de event sourcing, una implementación correcta y conveniente va a requerir tiempo y soporte continuo del equipo de desarrollo. Si hubiera una herramienta para manejar event streams, construir snapshots y notificar a otras partes del sistema cuando algo cambia, sería muy útil. Afortunadamente esa herramienta existe: es EventSource, un sistema OSS de event sourcing.

Hay algunos riesgos en adoptar esa herramienta, pero los beneficios son mucho más prometedores en términos de tener un historial inmutable de cambios, proyecciones (snapshots) automáticas y notificación a los suscriptores de eventos específicos.

## Decisión

El enfoque de event sourcing nos da un historial completo de cambios y puede ayudar a investigar problemas y reclamos de usuarios. Con el soporte del storage de EventSource, el problema principal de sincronizar actualizaciones y read models se vuelve manejable.

## Consecuencias

Un sistema nuevo puede usarse de forma subóptima hasta que los desarrolladores capten la idea detrás del event sourcing y adopten patrones de trabajo para este nuevo paradigma.

Preferible arrancar con una solución SaaS para eliminar problemas de soporte y escala.
