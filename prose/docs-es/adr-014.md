# ADR 014 · Estrategia de despliegue

Fecha: 2020-11-20

## Estado

Propuesto

## Contexto

Una vez implementada la solución, tiene que ser barato desplegarla, mantenerla y escalarla. Actualmente hay varias opciones a considerar como plataformas de despliegue: servidores on-premise, soluciones serverless, orquestación de contenedores como Kubernetes (on-premise o como PaaS), u OpenShift, la versión empresarial on-premise de Kubernetes. Finalmente, podríamos elegir usar servidores virtuales provistos por AWS o Azure.

## Decisión

Decidimos ir con máquinas virtuales (instancias EC2) en AWS por dos razones. Primera: podemos arrancar con instancias mínimas y decidir escalar hacia arriba (escala vertical) en CPU y memoria. Cuando alcancemos los límites del upsizing, lo natural es escalar hacia afuera (escala horizontal) aumentando la cantidad de instancias corriendo. Segunda: el escalado horizontal se adhiere a nuestra arquitectura, donde podemos escalar componentes individuales de nuestro sistema según la carga de cada componente. Otra decisión detrás de descartar soluciones populares como Kubernetes es el esfuerzo de trabajo que hay que invertir en la plataforma: desde aprender Kubernetes hasta aprovisionar un cluster de Kubernetes con monitoreo, métricas y red entre servicios, como una service mesh.

## Consecuencias

Usar micro instancias EC2 mantiene los costos bajos. Además, usaremos contenedores (Docker o similar) para el desarrollo de la aplicación y los pondremos detrás de un reverse proxy.

**Positivo:** Bajo costo, baja huella cognitiva, mantenimiento fácil.

**Negativo:** Vendor lock-in.
